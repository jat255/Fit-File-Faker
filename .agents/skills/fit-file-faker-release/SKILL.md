# Fit File Faker releases

Use the repository's current `release.sh`, `AGENTS.md`, and `.github/workflows/publish_and_release.yml` as the source of truth. A pushed release tag publishes to PyPI, creates a draft GitHub release, and triggers changelog and documentation updates; publishing is a separate action from preparing a release.

1. Determine the requested scope and version. Inspect the latest release tag, `pyproject.toml`, and commits since the tag; recommend a version from the changes if one was not specified. Ask for the version if it cannot be determined. Do not publish when asked only to prepare or review a release.
2. Check the current branch, working tree, remote `main`, and existing local and remote tags. Preserve unrelated changes. Release from an up-to-date `main` unless the user explicitly directs otherwise. Stop and explain conflicts, duplicate tags, or unexpected repository state rather than bypassing checks.
3. Inspect every subject with `git log --format='%h %s' <previous-tag>..HEAD`. Check both the repository's conventional-commit policy and the current git-cliff parser in `pyproject.toml`; report subjects that are invalid or would be omitted. The script has exceptions for some subjects, so its validation alone is not sufficient. Do not rewrite published history without authorization.
4. Run the relevant local tests, lint, and package build; resolve failures before release. Draft release notes from all commits since the previous release, including appropriate credit to outside contributors. Inspect commit authors, co-author trailers, and linked pull requests where available; distinguish contributors from merge or automation accounts and avoid guessing identities. Review the version/date/lockfile changes. For preparation only, make the requested reviewable changes without creating or pushing a release tag.
5. Present the complete draft release notes and proposed version to the user. Explain that pushing the release tag starts PyPI publication and creates the GitHub release, then obtain explicit confirmation to publish before pushing the tag or taking any other publication action. An initial request to release does not replace this confirmation. Honor requested edits and any narrower scope.
6. After confirmation, use `./release.sh <version> [release-message]` after reviewing its current behavior. It updates `pyproject.toml`, `fit_file_faker/__init__.py`, and `uv.lock`, then prompts to commit, create an annotated tag, and push the branch and tag. Respond to prompts only within the user's authorized scope. Do not silently accept warnings about a dirty tree or unexpected branch. If interrupted, inspect the commit, tag, and remote state before retrying; avoid duplicate publication.
7. Monitor the tag-triggered GitHub Actions release workflow for the exact tag and commit, and inspect failed jobs if it does not succeed. Confirm the build, PyPI publication, GitHub release and documentation jobs complete successfully. Also check any other release-related workflows triggered by the tag. Do not report success or publish the GitHub release if a required job fails; report the failure and a concrete recovery path. Respect preparation-only scope.
8. Complete the GitHub release for an explicitly requested release. The current tag-triggered workflow creates the draft and uploads signed distributions; creating a second release for the same tag would make that job fail. After the workflow succeeds, inspect `gh release view v<version>` and its assets. Use `gh release edit` to add the approved release notes and publish the draft (`--draft=false`), unless the user requested a draft. Preserve the uploaded assets. If the workflow succeeds but the draft or expected assets are missing, stop and investigate. If the workflow changes so it no longer creates a release, create one with `gh release create --verify-tag` and approved notes instead.
9. Report the version, commit, tag, local verification, Actions results, GitHub release URL and draft/published status, and which publication steps completed. Do not claim PyPI publication succeeded without evidence.
